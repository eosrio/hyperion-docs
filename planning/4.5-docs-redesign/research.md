# Hyperion 4.5 documentation redesign research

Research date: 2026-10-20. This is a source audit and proposal, not release acceptance or a replacement of the published site.

## Evidence and status boundaries

- **Docs baseline:** `eosrio/hyperion-docs` master, `3f6759653e2c2c3ccf5ed72ebe61cacde6d2b0d8`. All 24 content Markdown files, the contributor README, and `mkdocs.yml` were read. All 24 content pages are represented in the navigation. The baseline has operator, developer, API, and one operations grouping, but no 4.5 migration, extension authoring, support matrix, or release-status section. [Navigation](https://github.com/eosrio/hyperion-docs/blob/3f6759653e2c2c3ccf5ed72ebe61cacde6d2b0d8/mkdocs.yml#L29-L60)
- **History API source baseline:** local branch `release/4.5`, HEAD `79af10986bc0e2aa84cce3788aea202d23547818`; package version is still `4.0.7`. This audit does not independently establish which GitHub tag is the latest published release. `CHANGELOG.md`, the action-query guard implementation, `hyperionConfig.ts`, and related tests have local edits. Observations about those edits are **working-tree evidence**, not permanent-release claims. [Committed package](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/package.json#L1-L20)
- **Accepted 4.5 design:** the current local `hyperion-tools/docs/architecture/hyperion-4.5.md` explicitly says it is a working architecture based on operator-approved decisions and that its requirements are not claims of completed implementation. That file, its roadmap, and some related architecture files have local modifications above tools HEAD `81da2f26de84b655ace531c073e9dc58e05d876c`. Cite their current repository-relative paths and lines when discussing the current design; do not present the local text as a released artifact. Sources: tools working tree, `docs/architecture/hyperion-4.5.md:3-35`; `docs/roadmap/hyperion-4.5.md:1-8,144-157`.
- **Extension foundations:** SDK main `9331341e37716177bc2b38989918b9fe1e4fbf14` and Wire main `5218f0ae26f5acea737b8acc8c9ae3b628084bc1` explicitly describe development scaffolds with no compatible implementation release. Catalog branch `docs/hyperion-45-catalog-foundation`, HEAD `421fb7d8f779e3e7dc6e20c3e8ac4cffcb14fcfc`, preserves legacy entries without declaring 4.5 compatibility. [SDK status](https://github.com/eosrio/hyperion-sdk/blob/9331341e37716177bc2b38989918b9fe1e4fbf14/README.md#L1-L20), [Wire status](https://github.com/eosrio/hyperion-wire-plugin/blob/5218f0ae26f5acea737b8acc8c9ae3b628084bc1/README.md#L1-L27), [catalog status](https://github.com/eosrio/hyperion-plugins/blob/421fb7d8f779e3e7dc6e20c3e8ac4cffcb14fcfc/README.md#L13-L32)

The public site should distinguish **stable**, **4.5 preview**, and **accepted design / planned**. A package scaffold, merged architecture, or tool benchmark cannot change a planned capability into a supported product feature. Publish the exact support matrix and tested component pins when qualification exists. This directly follows the roadmap's requirement to publish operator guidance as behavior becomes qualified and its M4 integrated release gate. Source: tools working tree, `docs/roadmap/hyperion-4.5.md:19-29,54-62,159-169`.

## New 4.5 documentation required

### Release-critical operator and consumer material

1. **4.5 release center and support matrix.** Exact supported chain/protocol, platform, dependency, backend, plugin/SDK/adapter combinations; stable versus preview; known limits; dates and qualification evidence. MongoDB-only launch is allowed by accepted design if WormDB is deferred. Do not promise dual-backend qualification until demonstrated. Source: tools working tree `docs/architecture/hyperion-4.5.md:18-35,137-144`; `docs/roadmap/hyperion-4.5.md:54-58,84-94`.
2. **Upgrade to 4.5 without discarding history.** Supported starting versions and index layouts, preflight inventory/backups, exact-artifact installation, retained Elasticsearch verification, separate projection initialization/catch-up/readiness, acceptance queries, rollback boundary. “No mandatory full reindex” is a release requirement, not evidence it already passes. Source: tools working tree `docs/architecture/hyperion-4.5.md:18-21,97-107,151-154`.
3. **History, state, finality, and availability.** Explain independent history/state progress; reversible-head default and irreversible-only option; forks and affected query pauses; incomplete projections; retryable unavailable responses; explicit last-valid mode, completeness metadata, and cached view semantics. Header names/status details remain implementation design work: do not invent them. Source: tools working tree `docs/architecture/hyperion-4.5.md:22-25,73-87,112-132,165-169`.
4. **Projection lifecycle.** Allowed contract scope, ABI deployments versus immutable mapping revisions, declared initialization/coverage, initialization/rebuild/catch-up, validated activation, failure isolation, bounded recovery and unavailable historical inputs. Document reloadable declarative mappings separately from executable hooks/native restarts. Source: tools working tree `docs/architecture/hyperion-4.5.md:89-118`.
5. **Backends and extensions.** One selected active state backend per chain; capabilities; tested adapter versions separate from engine versions; initialize/validate/cut over; all enabled state domains switch together; trusted executable code and controlled operator updates. Source: tools working tree `docs/architecture/hyperion-4.5.md:75-87,135-156`.
6. **AtomicAssets / AtomicMarket and Wire guides once qualified.** Enablement, contract/network scope, backend requirements, endpoint compatibility and tested deviations. Parity obligation is the full API against pinned atomicassets-api 2.7.0 commit `0aabc47dcf8bd0804d4dcecb336c90fc02a9c89e`; Wire requires a pinned new-testnet profile across applicable Node/Rust paths. Neither scaffold is a working current release. Source: tools working tree `docs/architecture/hyperion-4.5.md:18-35,57-60`; [Wire scaffold](https://github.com/eosrio/hyperion-wire-plugin/blob/5218f0ae26f5acea737b8acc8c9ae3b628084bc1/README.md#L16-L27).

## Source-derived references and checks

There is an existing generation seam. Route modules already define Fastify schemas; `generateOpenApiConfig` selects dynamic OpenAPI mode and package version; server registers Swagger UI at `/docs`, proxies `/v2/docs`, loads plugin routes, registers core routes, then calls `fastify.swagger()`. Use a deterministic release fixture to export a versioned spec and render reference pages from it. Record source commit, core/plugin pins, and generation time. No need to hand-maintain a second parameter table. [OpenAPI configuration](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/config/open_api.ts#L42-L67), [Swagger setup](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/server.ts#L226-L251), [compatibility proxy](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/server.ts#L344-L349), [registration/export](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/server.ts#L390-L409)

Generation does not complete schema quality. For example, the transaction route defines request parameters but no explicit response schema, whereas the account route has a response schema. Add response/error examples, generic indexed-field filters, proxy semantics, finality, limits, and consistency contracts. Keep explanatory recipes authored by humans; generated schema tables are the exact mechanical source. [Transaction schema](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/routes/v2-history/get_transaction/index.ts#L6-L35), [account response schema](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/api/routes/v2-state/get_account/index.ts#L19-L62)

Configuration reference should derive field/type information from `src/interfaces/hyperionConfig.ts` Zod schemas and `hyperionConnections.ts`, while defaults must be traced to runtime assignments and reference configs. Type optionality is not a default and a sample file can override runtime defaults. Redis currently supports authentication, TLS, and Sentinel pass-through despite docs showing only host/port. Source: API working tree `src/interfaces/hyperionConfig.ts:351-414`; [connection contracts](https://github.com/eosrio/hyperion-history-api/blob/79af10986bc0e2aa84cce3788aea202d23547818/src/interfaces/hyperionConnections.ts#L33-L59).

Proposed docs CI gates: internal links/redirect manifests; all fenced JSON parses; runnable curl/JS examples against fixed fixtures; generated spec and route inventory diff; declared config keys/defaults checked against source; pinned install smoke test ending in health plus real history/state queries; changed runtime contract requires corresponding docs review. Live public provider health is a separately timestamped check, not a deterministic build gate. Destructive repair/reset examples require explicit scope and evidence paths, not generic copy-paste commands.
